## 先說清楚：這個方法的核心是什麼

我沒有把影片看一遍，然後憑印象設定幾個甩頭角度。實際做法是把兩支影片拆成影格，記錄能看得清楚的鼻尖、眼睛、耳朵、舌頭和腳的位置，再用這些線索調整現有骨架。每改完一輪，就讓 Blender 算出真正變形後的模型，重新看畫面、量腳底、檢查穿插。

它比較像先把舞步看懂，再一個部位、一個部位教模型做。不是影片裡的任何像素都要硬套到模型上，也不是只要頭會左右晃，就算抖毛完成。頭、頸、胸、背、耳朵、舌頭和四隻腳必須一起成立。

最後還有一道檢查：把 GLB 匯出去，再重新載入 Blender。如果重新載入的狗和編輯中的狗不同，工作就還沒完成。這次真的在這一步抓到時間起點偏移，修正後才交付。

## 第一步：先看懂影片，暫時不要轉骨頭

兩支影片都約五秒、24 fps、1280 × 720，各有 121 張影格。先把它們拆開，排成每隔幾張就能看一眼的總覽。這樣才能看出起始站姿、開始甩動、主要抖動、低頭收尾和回到站姿的順序。

最關鍵的發現是：這兩支是分別生成的 AI 影片，不是兩台攝影機同時拍同一隻狗。正面開始甩動的時間和側面不同；某個時刻正面低頭，側面可能還在抬頭。耳朵的形狀也會在生成過程中拉長、扭曲。

如果 Claude 把同一幀號當成同一個姿態，同時要求模型滿足兩支影片，它會被互相衝突的要求拉扯。結果常見的是頭角度怪、脖子折太多、腿滑動，或耳朵被拉成奇怪的形狀。

這次的決定是：正面用來控制鼻尖、眼線和甩頭的節奏；側面用來檢查身體蹲低、腿如何支撐，以及側看是否合理。側面依動作階段對齊，四格對照有保留它實際使用的來源幀號。

| 正面來源幀 | 對應側面來源幀 |
|---:|---:|
| 0 | 0 |
| 22 | 12 |
| 32 | 22 |
| 86 | 80 |
| 98 | 90 |
| 120 | 120 |

中間的時間用直線補進去。例如正面 F60 對應側面約 F52，而不是側面 F60。這是一個工作上的階段映射，不代表兩支影片從此變成精確的雙視角量測。

**這一步做到什麼程度才可以往下？** 能指出起始、抖動開始、主要抖動和收尾的影格，而且能說明兩支影片哪些地方一致、哪些地方互相矛盾。還沒釐清，就先不要大量設定關鍵幀。

## 第二步：先摸清楚模型能怎麼動

我先透過 Blender MCP 匯入原始 GLB，列出物件、骨頭、骨頭的父子關係、原始動畫和蒙皮權重。蒙皮權重可以白話理解成：每一塊皮膚分別跟著哪些骨頭走、各跟多少。

這隻狗有 57 根骨頭、7,156 個頂點、12,510 個三角形，原本有 27 個動畫。骨架叫 `Arm_Beagle`，狗的網格叫 `Cartoon_Beagle`。每邊耳朵只有兩節骨頭，舌頭有四節。這些條件決定了它能做到多細的彎曲。

接著我停用原本的動畫疊加，讓模型回到原始站姿，從正面、側面和三分之四視角各渲染一次。先確認左右、前後、地板方向和狗的大小，再開始配影片。原本的輔助物件 `Icosphere` 不參與狗的渲染。

請保留原始 27 個動作。本次新增的動作是 `Body_Shake_Reference_Loop`；原本的抖毛動作保留為 `Body_Shake_Original`。接手修改時另存新版本，讓使用者能回頭比較。

**完成條件：** Claude 能說出哪些骨頭控制頭、頸、胸、耳、舌和四腳，也能看懂網格跟著骨頭如何變形。不要假設任何 GLB 都有相同骨名、單位或軸向。

## 第三步：把影片中可見的線索變成可量的資料

這次沒有使用需要另外訓練的狗姿態模型。我用影像顏色和位置範圍找候選點，再排除明顯不合理的結果。鼻子是深色、周圍通常有較亮的口鼻毛；眼睛是鼻子上方的兩個深色區域；舌頭有粉紅色；腳有較白的區域。

鼻尖最穩定，所以它是主要控制點。兩隻眼睛都看得清楚時，眼睛連線的斜度能告訴我們頭往哪邊歪。閉眼、轉頭或耳朵遮住眼睛時，量測就不可靠，這些影格要降低信任，不要硬把一塊陰影當成眼睛。

耳朵先找棕色輪廓，再找朝外或朝上的端點。這只是提示耳朵該往哪裡甩，不能拿它來證明耳朵真的有那麼長。舌頭的粉紅面積則幫助判斷什麼時候收回、什麼時候伸出，不能直接當成三維舌頭長度。

側面也量鼻尖、胸腹上下輪廓及前後腳的可見落點，供相機與姿態檢查使用。但本次沒有把所有側面量測逐幀加入頭部求解；請誠實描述它主要提供校正與檢查，不要把工作說成精密的雙視角三維重建。

Claude 可以換成更好的辨識方法，但請保留「有把握的才當強約束，模糊的只能當提示」這個判斷。

**完成條件：** 每張影格有可追溯的點位或缺值，並輸出畫上標記的總覽。只留下數字，沒有看標記是否落在正確部位，還不算量測完成。

## 第四步：先把攝影機對準，才知道是相機錯還是姿態錯

同一隻狗，相機偏一點、放大一點，看起來都會不一樣。如果一開始相機就沒對準，Claude 很容易把狗的骨頭扭壞，只為了補償畫面構圖。

我用起始站姿的鼻尖、眼睛和腳去配相機，主要調整觀看方向、俯仰角、大小，以及畫面左右上下的位置。這次採正交相機，可以理解成遠近透視較小、方便做畫面位置比較的相機。

先讓起始站姿大致對齊，再固定相機，用骨架去追蹤動作。前面配好相機後，不要每一幀都移動相機追鼻子，否則鼻尖誤差看似變小，實際上狗可能根本沒有做出正確動作。

**完成條件：** 起始站姿的主要控制點對齊得合理，三個視角都沒有方向弄反；相機資料存檔，後面每幀使用同一套相機。

## 第五步：讓頭、頸和身體分工，而不是整隻狗一起轉

全身抖毛不是把一根頭骨或整個根骨左右旋轉。頭會快速甩，脖子承接方向，背部跟著扭，腿要支撐重量，胸口則不能整塊倒進前腿。

我先把鼻尖上下移動拆成兩部分：慢慢蹲低的趨勢，以及快速抖動。慢的部分用來控制身體下降；快的部分用來輔助估計甩頭。眼線可靠時，再加入頭歪的方向。

接著用數值求解找出一組合理的頸、頭角度，使模型鼻尖投影到畫面後接近影片鼻尖。兩眼看得清楚的影格，也一起比較模型眼睛的位置。所謂「求解」，就是讓電腦反覆試角度，挑一組畫面誤差較小、姿態也沒有超出限制的結果。

為了避免電腦為追一個點把頭折得很怪，我另外限制頭和頸的轉動範圍，並加入姿態提示。這些提示不是影片直接量出來的三維角度，而是為了在資訊不足時維持合理姿態。

脊柱幾節骨頭分攤身體彎曲，整體下降最大約四公分。這是配合這隻狗尺寸的本次設定，換一個模型時要重新看比例，不能把四公分當成所有狗都適用的答案。

**完成條件：** 正面鼻尖與甩動方向能對上，側看脖子與背部合理。這次最終鼻尖投影誤差的中位數約 0.615 像素，最大約 5.265 像素；它只代表鼻尖這個點，不代表整隻狗與影片一模一樣。

## 第六步：先讓腳站穩，再追求甩得漂亮

腳最容易把動畫的問題暴露出來。身體一下降、脊柱一轉，四隻腳如果照著一起轉，就會離地或穿地。只看頭很像影片，整隻狗仍可能像在溜冰。

我先在三維空間訂出四隻腳的目標位置，再反過來算腿要彎成什麼角度。這叫反向運動學，通常簡稱 IK。可以想成先告訴狗「腳放這裡」，再讓它自己找到腿的彎法，而不是隨便彎腿後才猜腳會落在哪裡。

本次前腳在開始抖動時逐步拓寬站距：每邊約 4.1 公分、向前約 1.1 公分，主要抖動期間維持支撐，收尾再回原位。換站位時加入小小的抬腳弧線，開始約九毫米、收尾約六毫米，讓位置轉換看起來像放腳，而不是貼著地板橫移。

原始腳掌骨頭不在腳底，所以不能只量骨頭是否在 Z=0。我量的是變形後真正腳底頂點的最低位置，再修正腿部。腳掌也要反向補償父骨頭的旋轉，讓它接近起始的水平姿態。

我最初只調整影片的整幀，後來發現兩個整幀之間仍會稍微離地。因此把五秒動作細分成每四分之一幀一個時間點，共 481 點，再重算腿和腳掌。這不是為了讓輸出影片變成 96 fps，而是為了讓插值時更穩。

**完成條件：** 落地階段量腳底對地板的誤差；抬腳階段量腳底對預定抬腳弧線的誤差。這次最大約 0.091905 毫米。前腳最高約九毫米，是刻意換站位，不是漂浮九毫米的誤差。

## 第七步：耳朵要有延遲，舌頭要跟嘴巴一起收放

耳朵不會和頭完全同拍，它會受到甩動帶動、晚一點反應。初版用頭部約晚一張影格的方向當耳朵提示，再用影片的耳尖位置修正；之後發現部分角度會讓耳朵進入頭裡，就限制耳根和耳尖的可動範圍。

所以最後結果不是單純「頭延遲一幀就完成」。它經過了影片耳尖的對位，也經過避免穿插的修正。為了保留自然長度，耳骨沒有縮放；兩節骨頭能形成的彎曲有限，耳尖曲線仍和 AI 影片不同。

舌頭則依影片的粉紅可見面積判斷收放。在快速抖動、嘴巴收起的階段，第一節舌骨沿局部長度方向縮短，其餘舌骨調整方向，讓它往口內收。收尾再恢復。這是現有骨架條件下的做法，不是精密的口腔肌肉模擬。

閉眼也有嘗試使用現有眼皮骨頭，但模型的閉眼外觀仍與影片有差異。Claude 接手若要改善，請把它當成尚可提升的部位，而不是認為它已經逐像素符合。

**完成條件：** 耳朵的甩動方向與階段合理，口部收起時舌頭沒有露出不合理的尖角；逐幀檢查自由端是否穿入頭部。

## 第八步：穿插要看真正的皮膚，不能只看骨架

骨頭彼此沒碰到，不代表皮膚沒有相交。腿外面的皮膚可能被胸口擠穿，耳朵骨頭也可能在頭外、耳朵表面卻有一部分進頭裡。

我讓 Blender 算出每個時間點的實際變形網格，再用表面相交檢查找出可疑幀。耳朵與舌頭查自由端邊線有沒有跨過頭部表面；腿則查自由區邊線有沒有跨進胸腹或其他腿。

這次真的抓到胸口與右前腿相交。只把肘往外推還不夠，因為胸口還在大幅側翻。我把胸部最後一節的累積側翻降到原本約三成，再補償頸部，使頭的整體方向盡量維持原來的對位；接著重新算前腿和落腳。

這裡有個很容易漏掉的順序：改胸口之後，前腿姿態就可能變；前腿一變，腳底就要重量。不能修完胸口，卻拿修之前的腳底數據宣布全部通過。

另外，單純找「離表面最近的點」有時會被凹陷表面或法線方向誤導。它適合找疑點，不適合單獨當成穿插已證實的結論。要一起看邊線穿越表面的結果、當幀畫面，以及哪些頂點在動。

**完成條件：** 最終版本在 481 個取樣點的指定檢查區域沒有查到交叉，同時用三個視角看過。這個檢查有範圍，不能寫成所有三角形、任何連續時間都絕對不會自交。

## 第九步：Loop 要連姿態、速度和播放範圍一起處理

第一幀和最後一幀長得一樣，是基本條件。如果最後一幀還在快速甩、下一瞬間卻接回靜止的第一幀，看起來仍會一頓。

這次本來就有起始站姿和收尾站姿，所以我讓起始、結束回同一姿態，接縫兩邊保留靜止區段。這樣首尾的姿態相同，接縫附近的速度也接近零。各骨頭使用四元數旋轉，並讓相鄰四元數保持同一符號方向，避免數學上等價的旋轉被插值成意外轉圈。

Blender 中 F1 是時間零，F121 是五秒的閉合位置。動作資料包括 F121，但播放只用 F1–F120。因為 F121 就是下一輪的 F1，不必在影片裡多播一張重複站姿。

我比較了首尾骨頭矩陣、實際網格頂點，以及正面、側面、三分之四視角的渲染。這次三種比較的首尾差異都是零。對照影片播放三輪共十五秒，讓人可以直接看接縫是否跳一下。

如果 Claude 改成整段持續抖動、沒有靜止區段的 Loop，就要另外配首尾速度；不能只複製最後一幀，也不能把本次的靜止收尾策略硬套到另一個動作。

## 第十步：匯出成功，只代表檔案寫出來了

為了保留每四分之一幀的腳底修正，GLB 以 96 Hz 取樣。編輯中的 Blender 仍用 24 fps；匯出時暫時把時間軸放大四倍，匯出完就還原。

這一步最初出現一個問題：GLB 第一個時間不是零，而是約 0.0104167 秒。重新載入後，它的關鍵幀落在另一組時間位置，快速甩耳就和原動畫錯開。這不是可以忽略的小事，因為偏一點時間，快速動作的幾何差異就可能很大。

修正方法是讓匯出動畫從零秒開始，再把重新載入的動畫對齊 Blender 原本的 F1。接著在 481 個時間點比較變形後的模型。最終 GLB 與 Blender 的最大幾何差異約 0.000782 毫米，首尾網格差異零。

GLB 只匯出狗的骨架、網格和本次 `Body_Shake`，地板、燈、攝影機都不帶出去。其他 27 個原動畫則保留在 `.blend`，方便編輯與比較。

**完成條件：** 匯出的時間真的為 0–5 秒、首尾通道相同、重新載入後動作與編輯版本一致。讀到「export finished」還不夠。

# 第二部｜技術實作與重跑順序

這份附錄對應 [第一部白話教學](#第一部白話教學與完整交接)。它保留本次實際設定、資料結構、數學轉換、腳本相依順序與踩坑。這些數值是這隻 Beagle 的設定，不是通用的狗動作規格。

## 1. 執行分成兩邊

**本機 Python** 負責拆影片、點位量測、相機擬合、骨架數值求解、IK、製作比較圖與編碼影片。主要套件為 NumPy、SciPy、OpenCV、Pillow；另使用 FFmpeg／FFprobe。

**Blender MCP** 負責在 Blender 中讀骨架與權重、建立動作、設定關鍵幀、計算變形網格、渲染、匯出、重新匯入和保存 `.blend`。Blender 端用自己的 Python，不能假設它與系統 Python 的模組相同。這次 Blender 5.1.2 內有 NumPy；SciPy 求解在外部 Python 執行。

這次的呼叫鏈是：

```text
本機 mcp_call.py（MCP ClientSession）
    ↓ MCP stdio：execute_blender_code(code)
mcp_bridge.py（FastMCP）
    ↓ localhost TCP
Blender 已安裝 MCP 擴充（127.0.0.1:9876）
    ↓ 在 Blender 內執行 bpy 程式
實際 Blender 場景、動作、渲染與匯出
```

`mcp_bridge.py` 是為這次本機環境補上的 MCP 轉接器；不是對所有 Blender MCP 都通用的協定。Claude 若已有可用的 Blender MCP，直接把對應 `bpy` 程式交給它的執行工具即可，不必堆疊第二套。

本機擴充路徑：

```text
~/Library/Application Support/Blender/5.1/extensions/user_default/mcp
```

TCP 請求與回應分隔符是零位元組 `b'\0'`，本次請求為：

```python
payload = {'type': 'execute', 'code': code, 'strict_json': True}
sock.sendall(json.dumps(payload).encode() + b'\0')
```

不能把別套 MCP 的 `execute_code` JSON 直接套到這個擴充。先確認自己的工具格式，再送一段只回報版本、場景與物件的唯讀測試。

## 6. 主求解：相機、慢蹲低和快速甩頭

`05_fit_motion.py` 先用初始鼻、眼、四腳配正面相機。後腳影像控制點部分是人工指定，權重較低，並不是全部由自動辨識得來。

本次最終相機參數格式為：

```text
[方位角 rad, 仰角 rad, 像素縮放比例, cx px, cy px]
```

正面約 `[-1.447246, 0.220171, 932.73, 642, 347.99]`；側面約 `[0.04949, 0.24255, 850.012, 612.106, 354.92]`。精確值讀最終 NPZ，這裡只幫助理解量級。

數值相機用固定目標 `(0,0,0.25)` 建出畫面右向量與上向量，將三維點映射到二維。匹配到 Blender 時使用 `ortho_scale = 1280 / scale`，並設定 shift。拿同樣站姿渲染，確認外部投影與 Blender 畫面真的一致。

慢蹲低來自鼻尖 Y 的平滑趨勢，Gaussian sigma=3 影格；蹲低強度限制 0–1，Spine_base 的 Z 位移為 `-0.040 × 強度`。快速左右甩的提示來自鼻尖 X 扣除 sigma=4 平滑趨勢。

每幀求四個頭頸參數：頸俯仰、頭俯仰、左右轉、側歪。頸／頭分配約 20%／80% 的轉頭、28%／72% 的側歪。殘差包括鼻尖畫面誤差、可靠眼睛畫面誤差，以及較弱的姿態提示。

本次主求解 bounds，單位 rad：

```text
頸俯仰：-0.30 … 0.85
頭俯仰：-1.15 … 0.70
左右轉：-0.55 … 0.55
側歪：-0.90 … 0.90
```

眼睛與鼻尖只限制幾個畫面點，無法唯一決定完整三維姿態。bounds 與正則項的作用，是在多種可能角度間偏向較合理的動作。這些角度要搭配三個視角檢查，不是誤差越小越好。

脊柱由骨盆到胸逐節分攤彎曲和小幅扭轉；初版使用各節不同權重。尾巴也有克制的跟隨角度與較小正弦擾動，這是手工動作提示，沒有逐幀由影片量出尾巴的三維曲線。收尾全身回到 neutral。

## 7. 外部矩陣如何變成 Blender 的本地骨頭姿態

`kinematics.py` 的角度是外部約定的 XYZ 角，不是可直接填入每根 `pose_bone.rotation_euler` 的本地角。

對骨頭 i，以靜態骨頭起點 h 作支點，建立相對旋轉矩陣 D：旋轉部分為 `R`，平移部分為 `h - R @ h`。再沿父子鏈累積 `S_i = S_parent @ D_i`。Spine_base 額外帶入身體蹲低平移。

近似蒙皮的位置為：

```text
變形頂點 v' = Σ(權重 W[v,i] × S_i × 原始齊次頂點 v)
```

這個外部近似很好用來快速求解，但最後仍以 Blender evaluated mesh 為準；舌頭後來有額外的局部 scale，也要以 Blender 檢查。

寫入 Blender 時，`06_apply_preview.py` 先組成每根骨頭的目標 pose matrix：

```python
pose_i = S_i @ rest_i
# 有父骨頭：
basis_i = inverse(inverse(rest_parent) @ rest_i) @ inverse(pose_parent) @ pose_i
# 沒有父骨頭：
basis_i = inverse(rest_i) @ pose_i
```

將 `basis_i` 分解成 location、quaternion、scale。除了 Spine_base，其他骨頭 location 設零；除舌頭第一節外，scale 設 1。這能保留骨長，避免靠骨頭平移或伸長來偽裝姿態對位。

相鄰 quaternion 內積小於零時將新 quaternion 取負，避免同一旋轉的符號變換導致插值繞遠路。

## 8. 耳朵、口部和接縫的初版設定

`05` 先用頭部晚一影格的側歪方向做耳朵提示。`08_fit_ears.py` 再將原始耳尖頂點的加權變形投影與影片棕色輪廓端點比較，使用幾種初始抬耳角度求解。當耳尖因 AI 拉長而超出模型能到的位置，目標只作柔性提示，不改耳骨長度。

`11_prevent_collisions.py` 最終限制耳根 lift 約 -0.05–2.55 rad、第二節 curl 約 -0.25–0.55 rad，並限制兩節合計及另外兩軸的小幅轉動。這些是本模型實驗修正的角度界線，不是泛用碰撞演算法。

粉紅可見面積除以 450、sigma=0.65 平滑後，形成舌頭收回強度。來源時間 22–105 之間啟用，`tongue_1.scale.y = 1 - 0.72 × 強度`；其餘舌骨俯仰最終改為 `+0.04 × 強度` rad。

初版眼皮使用約 0.62 rad 的閉眼角度。沒有視覺證據證明它完全重現影片閉眼；接手時可改善現有權重或增加更適合的形狀控制，但那屬於新修改，應另外比較與驗證。

來源時間前段約 F0–F20、末段 F106–F120 回到 neutral，最後一點精確複製第一點。每條曲線加入 Cycles，密集關鍵幀用 LINEAR，避免 Bezier 自動把關鍵幀間拉出超調。

## 9. 腳、腳底與 481 點解算

腿目標先依起始位置固定，再加前腳站距變化。站距曲線用 PCHIP 控制點：

```text
t:       0, 22, 31, 84, 97, 120
stance:  0,  0,  1,  1,  0,   0
```

每隻前腳 X 向外約 0.041 m、Y 向前約 -0.011 m。初版依 hip/thigh/leg/shin 鏈解足骨位置；每次解完，用父骨頭旋轉的逆矩陣補償腳掌方向。

`09_correct_support.py` 用腳底頂點修正整幀目標，骨架物件 Z 加 `0.0001773 m` 的地面修正。腳底區域按 foot、claws、shin 權重合計 >0.6，且靜態 Z<0.022 m 選取。本次全部幾何單位依 Blender／GLB 的模型座標計算。

`12_subframe_support.py` 用 Slerp 把整幀旋轉細分到 0.25 幀，再逐點重算腿與腳掌；根部平移線性補點。腳底目標高度 h(t)：

```python
h = 0.0
if is_front_paw and 22 < t < 31:
    h = 0.009 * sin(pi * (t - 22) / 9)
if is_front_paw and 84 < t < 97:
    h = 0.006 * sin(pi * (t - 84) / 13)
error = abs(actual_sole_min_z - h)
```

後腳目標高度為零。`foot_targets` 儲存的是解算足骨的目標位置，不是腳底高度；不能拿它的 Z 直接與地面比較。

最終腳底誤差需從 `Blender逐幀驗證.json` 的最終 `soles_m` 重新算。這次最大約 0.091905 mm，換站位弧線段誤差最大約 0.011106 mm。不能使用 `max(abs(sole_z))` 當貼地誤差，那會把九毫米的刻意抬腳算進去。

## 10. 胸口與肘部修正的正確位置

`17_stabilize_chest.py` 把 Spine_05 **累積到世界約定空間的旋轉**拆成 XYZ，再把 Y 側翻乘 0.30，重算它對父骨頭的角度。接著補償 neck，使 neck 的原先整體方向盡量維持。它不是直接把本地胸骨某個 Euler 值乘 0.30。

這步會改變前腿的父鏈，所以後面接 `15_elbow_clearance.py`。`15` 增加前腿關節的側向解算自由度，肘外側位置目標約 `原始外距 + 0.023 × stance m`，同時維持腳位置與腳底目標弧線。

**`17` 不是可以重複跑任意次的操作。** 每跑一次都會再把現有累積側翻乘三成。要重試，從修正前的 checkpoint 還原，或重新建立該階段資料；不要對最終 NPZ 連續跑它。

本次矩陣補償優先保留頸與頭的旋轉方向，不能聲稱頭的位置也數學上完全不變。胸骨支點一變，後代位置仍可能稍移；最終鼻尖誤差就是在這些修正完成後重新計算。

## 13. Blender 5.1 的動作曲線與關鍵幀

本次使用 action 的 layers → strips → slots → channelbag 取得 fcurves，並不是直接假設 `action.fcurves`：

```python
for layer in action.layers:
    for strip in layer.strips:
        for slot in action.slots:
            bag = strip.channelbag(slot)
            if bag:
                for fc in bag.fcurves:
                    for key in fc.keyframe_points:
                        key.interpolation = 'LINEAR'
```

依本機 Blender 的 API 檢查，不要直接從記憶套舊範例。keyframe_insert 以 `frame=frame_times[i]+1` 寫入。每根骨頭寫 quaternion，Spine_base 寫 location，tongue_1 寫 scale。舊 NLA tracks mute，讓本次 active action 獨立生效。

場景播放設 24 fps、F1–F120；動作完整範圍 F1–F121，閉合點保留。

## 14. 實際網格驗證怎麼做

每個取樣點先 `scene.frame_set(整數, subframe=小數)`，更新 view layer，再從 dependency graph 取得 evaluated object。使用 `evaluated_object.to_mesh()`，把頂點乘實際 `matrix_world`，讀完以 `to_mesh_clear()` 釋放。

這是實際 Blender 蒙皮結果，不是只使用外部近似矩陣。

檢查包括：

1. F1 與 F121 的骨頭矩陣、網格頂點差異，以及 F1→F2、F120→F121 的變化。
2. Root_bone 的 X/Y 範圍。
3. 各腳底最低頂點、腳掌矩陣相對起始的角度。
4. 耳朵自由端、舌頭自由端邊線對頭部表面。
5. 腿部自由區邊線對胸腹及其他腿表面。

本次用權重門檻挑區域，再建立 BVH 表面，將各邊線沿線段做 ray cast。為避開表面貼合的數值接觸，線段起終點與碰點有約 10–20 微米的容差。它是指定區域的有限取樣檢查，不是完整所有三角形自交證明。

耳區主要選 Ear_02 權重較高、離耳根一定距離的自由端；舌區選 tongue_3/4 主導的自由端；胸腹與腿也依權重挑區域。原始 `10` 保留這些門檻，可清楚查到覆蓋範圍。

`ear_head_signed_proximity_flags` 是靠近表面的疑點，不直接等於穿插。最後判斷一起使用邊線穿越結果與當幀三視角。

原 `10` 主要寫 JSON，不會把所有完成條件都 assert。Claude 應另外讀 JSON、判讀腳底目標誤差，並設通過／未通過，不能把「程式跑完」等同「動作通過」。

## 16. GLB 回讀與結構驗證

`19_roundtrip_glb.py` 先記錄匯入前的物件與 action 集合，再匯入最終 GLB，找出新增骨架、網格與 action。GLB 時間零匯回 24 fps 的 Blender 通常落在 F0；本次把匯入 action 的 keys 與 handles 都 +1，對應原始 F1。

對兩個模型在 F1–F121、step 0.25 取得實際變形頂點。由於 glTF 可因 UV／normal 分裂頂點，不能直接要求頂點索引與總數相同。本次用 KDTree 比較匯入頂點到原始頂點的最近距離。

原實作是單向最近距離；它不能單獨排除某些原始頂點被漏掉。Claude 可加反向距離、包圍盒、材質與網格完整性檢查，讓它更完整；此擴充屬於接手後可增加的驗證，不是假稱本次已經做過。

本次 assert 最大幾何差異 <0.00002 m、匯入版本首尾差異 <0.000001 m；實際最大幾何差異約 7.82275e-7 m。通過後移除本次匯入測試物件與 action，再保存原場景。

`24_audit_delivery.py` 讀 GLB binary／JSON，檢查所有動畫通道：finite、時間單調增加、481 點、開始 0、結束 5、首尾相等。四元數 q 和 -q 代表同一個旋轉，端點比較取兩者中較小差異。

本次 171 通道包括骨頭 translation、rotation、scale 的 sampled channel；不要誤認為只有 171 根骨頭。最終仍是 57 骨。

## 17. 對照與交付證據

`16` 渲染三個視角各 121 張，包括閉合影格；`18` 使用 F0–F119 編成一輪、循環三輪共十五秒。`22` 另存完整 121 張四格 JPEG。

紅標記是影片鼻尖，綠標記是最終模型投影，青線是影片眼線。相機與動作修改後必須重產圖，不能把舊 render 和新的點位標記混用。

首尾 PNG 使用原始像素陣列比較；本次三個視角均零差異。輸出 PNG 的抗鋸齒與渲染採樣固定，讓比較可重複。

原 `18` 會重寫 `交付證據摘要.json`，`24` 再加回匯出結構、回讀與 hash。所以 `18` 之後要再跑 `24`，並使用新的腳底公式補入當版誤差。來源 SHA 用來確認輸入未改；交付 SHA 用來確認影片與檔案屬於同一個輸出版本。

## 18. 判讀 MCP 回應，別再把失敗包成成功

請同時檢查：

```text
MCP CallToolResult.isError
Blender 回應 JSON.status
必要 assert／實際產出
```

早期 bridge 未檢查內層 `status`，因此操作紀錄中有外層未報錯、內層 `status: error` 的例子。最終 `mcp_bridge.py` 已會把非 ok 回應 raise。紀錄不是只看 OK 字樣；要把內容讀完。

長時間渲染也要等工具或程序完成，再讀輸出。若工具呼叫有字數／時間限制，拆成「寫動作」「渲染某批」「做數值檢查」「保存」幾段，不以超時或暫時沒輸出判斷已成功。
